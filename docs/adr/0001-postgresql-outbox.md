# ADR 0001: PostgreSQL transactional outbox для пилота

- Статус: принято
- Дата: 2026-10-21

## Контекст

Создание заказа должно атомарно менять остатки и гарантировать последующую доставку заказа ресторану. Пилот работает с одной основной PostgreSQL, небольшим числом ресторанов и одним потребителем события. Отдельный брокер увеличит эксплуатационную сложность раньше, чем даст измеримую пользу.

## Решение

Оставить PostgreSQL transactional outbox источником интеграционных событий на этапе пилота. Worker забирает записи через `FOR UPDATE SKIP LOCKED`, повторяет доставку с backoff и jitter, переносит исчерпавшие попытки в dead-letter и поддерживает ручной replay. Получатель дедуплицирует события по стабильному event ID. Обработанные и dead-letter записи удаляются фоновым retention worker пакетами; pending не удаляются.

## Последствия

Запись заказа и события остаётся атомарной, а команда эксплуатирует один durable storage. Цена решения — polling PostgreSQL, ограниченный fan-out и дополнительная нагрузка на основную БД. Метрики backlog, oldest age, dead-letter и cleanup должны использоваться для контроля этой нагрузки.

Kafka, NATS или RabbitMQ рассматриваются повторно, если нагрузочный тест покажет неприемлемую нагрузку polling, потребуется несколько независимых потребителей, строгий порядок по ключу, длительный replay либо пропускная способность превысит возможности PostgreSQL outbox. Миграция должна выполняться через relay с сохранением текущих event ID и версий контрактов.
