# Контракт интеграционных событий

Platform API доставляет событие `order.created` версии 1 в ресторан методом `POST /integration/v1/orders`. Тело соответствует схеме [`order-created-v1.schema.json`](../api/events/order-created-v1.schema.json), а метаданные передаются обязательными HTTP-заголовками.

| Заголовок | Значение |
|---|---|
| `X-Event-ID` | стабильный UUID логического события, одинаковый во всех повторах |
| `Idempotency-Key` | тот же UUID, что и `X-Event-ID` |
| `X-Event-Type` | `order.created` |
| `X-Event-Version` | `1` |
| `X-Correlation-ID` | UUID заказа для сквозной корреляции |
| `X-Event-Occurred-At` | момент возникновения события в RFC 3339 с часовым поясом |

Получатель обязан дедуплицировать запросы по `X-Event-ID`. Ответ `2xx` подтверждает сохранение события; любой другой ответ или транспортная ошибка приводит к повтору с тем же event ID. После исчерпания попыток запись остаётся в dead-letter до ручного replay или истечения отдельного retention.

Версия меняется только при несовместимом изменении тела или семантики. Добавление необязательного поля допускается в текущей версии, поэтому получатель не должен отклонять неизвестные поля. Общий пакет `internal/eventcontract` формирует и проверяет metadata на обеих сторонах.

Обработанные события хранятся 7 дней, dead-letter — 30 дней по умолчанию. Очистка идёт пакетами и никогда не удаляет pending-записи.
