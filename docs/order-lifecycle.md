# Жизненный цикл заказа

## Состояния и владельцы переходов

Начальное состояние заказа — `pending`, версия — `1`. Каждый успешный переход увеличивает `version` на единицу.

Допустимые переходы ресторана:

- `pending → accepted`;
- `pending → rejected`;
- `accepted → preparing`;
- `preparing → ready`;
- `ready → delivering`;
- `delivering → delivered`.

Клиент может отменить заказ только в состояниях `pending` и `accepted`. После начала приготовления отмена должна выполняться оператором по отдельной политике, которая будет добавлена вместе с оплатой и возвратами.

Состояния `rejected`, `cancelled` и `delivered` терминальные.

## Конкурентные команды

Команда изменения состояния содержит `expectedVersion`. Сервер блокирует строку заказа в транзакции и сравнивает переданную версию с текущей. Если заказ уже изменился, сервер отвечает `409 Conflict`; клиент должен перечитать заказ и явно повторить допустимое действие.

Повтор команды, которая уже привела заказ в требуемое состояние, идемпотентен и возвращает текущее представление заказа.

## Причины

Для отклонения рестораном обязательны коды:

- `restaurant_busy`;
- `item_unavailable`;
- `restaurant_closing`;
- `other`.

Для отмены клиентом обязательны коды:

- `customer_changed_mind`;
- `wrong_delivery_address`;
- `other`.

Поле `reason` остаётся необязательным пояснением длиной до 500 символов. Бизнес-аналитика должна группировать операции по `statusReasonCode`, а не по свободному тексту.

## Остатки

При создании заказа остатки списываются в транзакции. Первый переход в `rejected` или `cancelled` возвращает все позиции на склад в той же транзакции, что и изменение состояния. Версионная проверка и блокировка заказа исключают двойной возврат.

## События

Создание заказа сохраняет `order.created` в transactional outbox. Следующий этап развития должен добавить версионированные `order.status_changed` события, inbox потребителей и восстановимый SSE с `Last-Event-ID`.
