# Состояние проекта и roadmap до рабочего продукта

Обновлено: 14 октября 2026 года.

## Цель

Довести текущий технический прототип до продукта, который можно безопасно развернуть в staging, провести через пилот с несколькими ресторанами и затем эксплуатировать с измеримыми SLO.

Рабочим продуктом считается система, в которой:

- клиент может зарегистрироваться, выбрать ресторан, оформить и оплатить заказ, получать уведомления и отслеживать доставку;
- ресторан управляет меню, остатками, сотрудниками и заказами, а все действия аудируются;
- оператор видит состояние заказов и интеграций, может повторить неуспешную доставку события и помочь пользователю;
- заказ, платёж и назначение курьера согласованы при сбоях и повторных запросах;
- сервис разворачивается воспроизводимо, восстанавливается из резервной копии и наблюдается через метрики, логи и трассировку;
- критический путь защищён автотестами, нагрузочными проверками и алертами.

- [x] серверный quote, проверка остатков и защита от overselling;
- [x] идемпотентное создание заказа;
- [x] транзакционная запись заказа, позиций, истории и outbox-события;
- [x] клиентский lifecycle заказа и SSE-обновления;
- [x] регистрация, вход, JWT access token и ротация refresh token;
- [x] профиль, адреса и история заказов пользователя;
- [x] кабинет ресторана, realtime-очередь и редактор меню;
- [x] OpenAPI, архитектурные схемы, unit-, backend E2E- и Playwright-тесты;
- [x] локальный запуск через Docker Compose и базовый CI.

Текущая стадия: функционально законченный прототип happy path. Он подходит для демонстрации и локальной разработки, но пока не готов к внешнему трафику и реальным деньгам.

## Принципы развития

1. PostgreSQL остаётся источником истины для заказов, пользователей, платежей и доставки.
2. Модульный монолит не разбивается на сервисы без измеримой причины. Сначала фиксируются границы модулей, события и SLO; отдельный процесс появляется при независимом масштабировании или владении.
3. ClickHouse используется для продуктовой и операционной аналитики, но не участвует синхронно в создании заказа.
4. Все побочные эффекты запускаются из надёжно сохранённых событий и должны быть идемпотентны.
5. В метрики и логи нельзя помещать email, адрес, JWT, API key и другие персональные или секретные данные.
6. Каждый этап заканчивается проверяемыми критериями готовности, а не только наличием кода.

- [x] сделать входящий endpoint ресторана идемпотентным по `event_id`;
- [ ] ввести inbox для входящих webhook/событий оплаты и доставки;

- [ ] добавить `Last-Event-ID`, heartbeat и восстановление пропущенных событий для клиентского и партнёрского SSE;

Готово, когда любое событие либо доставлено и дедуплицировано, либо явно видно в dead-letter очереди и безопасно переигрывается.

### P0.4. Наблюдаемость: минимальный обязательный контур

- [x] добавить единый OpenTelemetry SDK в API, worker и demo restaurant;
- [x] принимать и передавать W3C `traceparent`, `tracestate` и baggage между HTTP-вызовами platform API, outbox worker и demo restaurant;
- [ ] писать структурированные JSON-логи с `service`, `environment`, `version`, `request_id`, `trace_id`, `span_id`, `order_id` и `restaurant_id`: базовые поля и trace correlation готовы, остаётся унифицировать контекст всех доменных записей;
- [x] добавить `/metrics` для Prometheus с RED, Go runtime, PostgreSQL pool и outbox-метриками;
- [x] поднять локальный observability profile в Compose: Prometheus, Grafana, Loki, Tempo, Promtail и OpenTelemetry Collector;
- [x] настроить provisioning Prometheus, Loki и Tempo datasources, базовый dashboard и alert rules как код;
- [ ] добавить exemplars: переход из графика latency в trace и из trace в связанные логи;
- [ ] описать правила cardinality и запретить `user_id`, `order_id`, URL с UUID, email и address в labels;
- [ ] добавить runbook к каждому критическому алерту: базовые API/outbox runbooks готовы, расширять вместе с новыми SLI.

Минимальный набор метрик:

- RED для HTTP: `http_server_requests_total`, `http_server_request_duration_seconds`, `http_server_active_requests`;
- PostgreSQL pool: используемые, свободные и ожидающие соединения, acquire duration и ошибки запросов;
- заказы: число попыток и результат create/quote, конфликты idempotency, ошибки проверки остатков, переходы статусов;
- outbox: размер backlog, возраст самого старого события, попытки, длительность доставки и dead-letter count;
- SSE: активные соединения, ошибки отправки, переподключения и длительность соединения;
- Go runtime: goroutines, GC, heap, CPU и process health.

Обязательные Grafana dashboards:

- `Service overview`: traffic, error rate, p50/p95/p99 latency, saturation и версии приложений;
- `Order funnel`: quote → create → accepted → delivered, отказы и длительность этапов;
- `Outbox & integrations`: backlog, oldest age, retries, dead letters и ошибки по интеграции;
- `PostgreSQL`: pool, транзакции, locks, slow queries, размер и рост БД;
- `SSE`: активные клиенты, reconnect rate и ошибки;
- `Business pilot`: GMV, количество заказов, средний чек, отмены и время доставки без персональных данных.

Стартовые SLI/SLO для пилота:

- доступность create/quote API: 99,9% за 30 дней;
- успешность технического создания валидного заказа: не ниже 99,5%;
- p95 quote: до 300 мс, p95 create order: до 500 мс без внешних побочных эффектов;
- 99% outbox-событий доставлены не позднее 30 секунд;
- доля заказов, зависших без допустимого перехода более 10 минут: менее 0,1%;
- error-budget alerts: fast burn и slow burn, а не алерт на каждый единичный 5xx.

Готово, когда сбой критического сценария обнаруживается по алерту, локализуется через dashboard → trace → logs и имеет проверенный runbook.

## P2 — ClickHouse и продуктовая аналитика

ClickHouse вводится после стабилизации версий доменных событий. Он получает копии событий асинхронно и не влияет на транзакционный контур.

- [ ] утвердить схему аналитического события: `event_id`, `event_version`, `event_name`, `occurred_at`, `ingested_at`, `trace_id`, обезличенные измерения и properties;
- [ ] публиковать `order_created`, `order_status_changed`, `payment_*`, `delivery_*`, `notification_*` и frontend funnel events;
- [ ] доставлять события через broker/collector в raw MergeTree таблицу ClickHouse;
- [ ] дедуплицировать события по `event_id` и мониторить ingestion lag;
- [ ] создать materialized views для order funnel, GMV, conversion, cancellations, restaurant SLA и delivery time;
- [ ] подключить ClickHouse datasource к Grafana для бизнес-панелей;
- [ ] отделить техническую телеметрию Prometheus от бизнес-аналитики ClickHouse;
- [ ] добавить TTL, партиционирование, политику удаления пользователя и словарь данных;
- [ ] сверять ключевые агрегаты ClickHouse с PostgreSQL и алертить расхождения;
- [ ] провести нагрузочный тест ingestion и тяжёлых dashboard queries.

Готово, когда аналитический контур допускает переигрывание из сырого журнала, не содержит прямых персональных данных и его потеря не влияет на оформление заказов.

## Release gates

Перед пилотом:

- [ ] критический E2E проходит в CI и staging;
- [ ] нет открытых critical/high уязвимостей;
- [ ] проведены load test, restore drill и проверка rollback;
- [ ] настроены dashboards, SLO alerts и on-call контакты;
- [ ] dead-letter и replay проверены искусственным сбоем;
- [ ] персональные данные и секреты отсутствуют в логах, метриках и traces.

Перед production:

- [ ] успешно завершён ограниченный пилот;
- [ ] error budget не исчерпан минимум две недели;
- [ ] подтверждены RPO/RTO и план реагирования на инциденты;
- [ ] платежная сверка и возвраты проверены на sandbox и тестовых операциях;
- [ ] есть владелец каждого алерта, runbook и бизнес-критичного процесса;
- [ ] определены политика хранения данных, пользовательское соглашение и требования применимого законодательства.

## Не делать сейчас

- не переносить PostgreSQL-заказы или auth в ClickHouse;
- не начинать с Kubernetes, если один staging-host/managed container platform закрывает пилот;
- не выделять Catalog и Order в отдельные сервисы только ради названия «microservices»;
- не использовать `order_id`, `user_id` и адрес как Prometheus labels;
- не добавлять Kafka без нескольких независимых consumers или подтверждённой нагрузки;
- не подключать реальные платежи до появления webhook inbox, аудита, refund и reconciliation.
